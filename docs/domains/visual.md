# Domain: Visual

Everything that produces pixels: rendering, sprites, tilemaps, animation, UI,
materials, palettes. The largest domain by a wide margin, and the one where
Raster's identity lives.

**Crates:** `raster-render`, `raster-2d`, `raster-ui`, and five editors

## Why one domain

Animation is not a separate domain — it is a way of sequencing sprites, and it
shares the frame model, the palette and the preview surface with the sprite
editor. UI is not a separate domain — it draws through the same renderer, uses
the same fonts, the same palettes, the same materials.

Splitting these produces three editors that each redefine what a frame is and
what a palette is. Grouping them means the sprite editor, the tilemap painter and
the animation timeline are three views over shared concepts.

## Pixel-perfect rendering

This is the constraint that shapes the whole renderer, and it is not negotiable.
An engine that is 2D-first but renders pixel art with visible artefacts has
failed at the only thing that distinguishes it.

The rules:

- **Integer scaling.** The framebuffer renders at a fixed low resolution and
  scales by a whole number. A 3.7× scale produces uneven pixels; there is no
  version of that which looks acceptable.
- **Nearest-neighbour filtering**, everywhere, by default.
- **Snapping policy.** Sprite positions snap to the pixel grid — but the *camera*
  interpolates in sub-pixels so scrolling stays smooth. Getting this pair wrong
  produces either jitter or blur, and it is the single most common failure in
  2D engines.
- **Rotation policy.** Rotated pixel art must be explicitly chosen, since it
  necessarily breaks the grid. The default is off.
- **Letterboxing** rather than stretching, when the window does not match the
  target aspect.

## The renderer

`wgpu`, targeting Vulkan, Metal, DX12 and WebGPU from one backend. This also
means the browser is reachable later — which matters, since Rasterie already
lives on the web.

Structure:

- **Sprite batching** — one draw call per (texture, material, layer) group
- **Texture atlases** — packed at import; a sprite is a rect within an atlas
- **Layers** — explicit ordering, with sorting within a layer
- **Cameras** — orthographic, multiple, with viewports and per-camera layer masks
- **2D lighting** — normal maps, coloured lights, shadow casting from tiles.
  Optional, since many pixel art games want flat unlit rendering, but essential
  for a Terraria-like's caves
- **Post-processing** — a small chain: colour grading, screen shake, transitions,
  CRT-style effects for those who want them

## Sprites

```rust
pub struct Sprite {
    pub texture: AssetId<Texture>,
    pub frame: u32,
    pub tint: Color,
    pub flip_x: bool,
    pub flip_y: bool,
    pub pivot: Vec2,
    pub layer: Layer,
    pub material: Option<AssetId<Material>>,
}
```

A `.sprite` asset carries frames, pivot, and — when generated by Rasterie — the
parameters that produced it. That last part is what makes a Raster sprite
different from an imported PNG: it can be regenerated, recoloured against a new
palette, or varied.

## Palettes

A first-class asset, not a convenience.

Rasterie works in OKLCH and builds ramps with hue shifting — cold shadows, warm
highlights — which is the mechanism behind pixel art that looks hand-made rather
than mathematically darkened. Palettes carry that structure: ramps, not just
lists of colours.

Consequences worth having: swapping a palette recolours every sprite built on it,
so a whole game's mood is one asset; and palette-swapped variants (a red slime
and a blue slime) cost nothing.

## Tilemaps

The structural centre of a Terraria-like, and the reason tiles are emphatically
not actors.

- **Chunked storage.** The world is divided into fixed chunks, stored as compact
  arrays. Millions of tiles, loaded and unloaded around the camera.
- **Multiple layers** — background, main, foreground, liquids
- **Autotiling** — 47-variant bitmask, computed on edit and cached
- **Per-tile data** — collision shape, one-way flag, material, damage
- **Streaming** — chunks generate, load and evict as the camera moves
- **Runtime mutation** — a Terraria-like changes tiles constantly, so edits must
  be cheap: only the affected chunk's mesh and autotile neighbourhood rebuild

Only tiles with behaviour — a chest, a machine, a sign — get an associated actor,
linked by tile coordinate.

## Animation

- **Frame animation** — sequences of sprite frames, with per-frame duration
- **Events on frames** — a footstep sound on frame 3, a hitbox on frame 5.
  Essential, and often bolted on badly in engines that treat animation as pure
  playback
- **Property animation** — curves over reflected properties, so anything
  reflectable can be animated
- **State machine** — states and transitions with conditions, since character
  animation is otherwise a mess of booleans in gameplay code
- **Blending** — crossfades between states

The animation editor shares the frame model with the sprite editor rather than
redefining it. That sharing is the whole point of the domain grouping.

## UI

`raster-ui`, the retained-mode object-oriented toolkit described in
[architecture/editor.md](../architecture/editor.md). Used by games and by the
editor itself.

- **Widget tree** — objects with identity and persistent state
- **Constraint layout** — flex-like, plus anchors for HUD elements
- **Theming** — centralised tokens, so the visual identity is one file
- **Input routing** — focus, hover, capture, keyboard navigation
- **Text** — bitmap fonts first, since a pixel art engine needs pixel fonts more
  than it needs vector shaping

A `.widget` asset is authored in the UI designer and instantiated at runtime.

## Materials

2D shaders, authored as a node graph on `raster-graph` — the same foundation as
audio cues.

Realistic uses in 2D: outlines, flashes on hit, dissolves, water distortion,
palette cycling, scrolling backgrounds. Not a physically-based system; a small
set of composable effects.

## Open questions

- Whether 2D lighting is in from the start or added later. A Terraria-like needs
  it, but it complicates the renderer considerably.
- The tilemap chunk format, and whether it is an asset or a save-file concern
- Whether `raster-ui` can genuinely serve both game UI and the editor, or whether
  the editor needs its own toolkit
- How the sprite editor exposes Rasterie's parametric generation without becoming
  overwhelming to someone who just wants to draw
